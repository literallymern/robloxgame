# 01 · Technical Architecture

Status: **proposed in Milestone 0** (2026-10-26). Milestone 1 implements the code structure described here. Anything marked *proposal* is an implementation choice, not canon.

## 1. Guiding principles

1. **Server authority.** Money, permissions, ownership, arrests, health, equipment and records are decided on the server. The client only asks; it never tells the server what a price, balance, rank or result is.
2. **One source of truth per kind of data.** Every piece of data has exactly one owner system (see section 6). Nothing is stored authoritatively in two places.
3. **Code in Git, world in the place file.** Scripts live in this repository and reach Studio through Rojo. Terrain, buildings and props live in the Roblox place file. Large geometry is generated by builder scripts kept in Git, so it can be rebuilt.
4. **Small modules with clear jobs.** One service per domain (profiles, permissions, banking terminals, police, ...). No script manages unrelated systems.
5. **No framework lock-in.** A tiny in-house service loader instead of a third-party framework. Third-party libraries are vendored as single files only when they clearly earn their place (for example session-locked DataStores in Milestone 6).
6. **Fail safe.** A failing service is logged and isolated; it must not stop the other services from starting. A failed save never deletes data.

## 2. Where things live

| Kind of content | Stored in | Reaches Studio via | Edited by |
|---|---|---|---|
| Luau code (server, client, shared) | `src/` in this repo | Rojo (live sync) | Claude in Git; Justin pulls with GitHub Desktop |
| Configuration and lore constants | `src/shared/Config/` | Rojo | Git |
| Builder scripts (terrain, roads, blockouts, statue) | `src/studio/` | Rojo → `ServerStorage.StudioTools` | Git; **run once by Justin in Studio** |
| Service settings (streaming, lighting defaults) | `default.project.json` `$properties` | Rojo | Git |
| Terrain, buildings, props, the statue model | The place file on Roblox | Saved in Studio (File → Publish / Save) | Generated by builders, then refined by hand in Studio |
| UI images (flag, emblem) | Roblox asset library | Asset IDs in `src/shared/Config/Assets.luau` | Justin uploads; IDs go into Git |
| Player data (non-financial) | Roblox DataStores | Runtime | Game servers only |
| Money, businesses, loans, AVK, property, fines | Economy bot database (`discord/bot`) | Economy Bridge (HTTPS) | Bot only (see section 6) |

Rojo only syncs **from files to Studio**. The map is therefore never placed under a Rojo `$path`; otherwise Rojo could remove hand-built parts. Place-file backups: *File → Save to File As* (`.rbxl`) after every map milestone, kept outside Git (the `.gitignore` already excludes place files).

Gameplay objects in the map (ATMs, doors, cells, garages, court benches, hospital beds) are found by **CollectionService tags and Attributes**, not by hard-coded paths. Example: a part tagged `BankTerminal` with attribute `Facility = "CentralBank"`. Builders and hand-built parts only need the right tag; the code finds them, also when instance streaming loads them later.

## 4. Service model

Each server service is a ModuleScript with the same shape:

```lua
local MyService = {}
MyService.Name = "MyService"
MyService.Dependencies = { "LogService", "PermissionService" }

function MyService.init(services)  -- wire up, no yielding
end

function MyService.start()        -- may spawn loops and connect events
end

return MyService
```

`Main.server.luau` loads all services, sorts them by `Dependencies`, calls every `init` inside `pcall`, then every `start` in its own thread. A failure is logged with the service name and does not stop the others. The client uses the same pattern with controllers.

## 5. Networking and security rules

- All remotes are declared in one file (`Shared/Net/Remotes.luau`) with argument types and limits. The server creates them; nothing else may create remotes.
- Client → server only. Remote functions are never invoked on the client by the server.
- Every request is checked in this order: rate limit → argument types and ranges (reject NaN, infinity, huge strings) → permission → distance to the interaction point → business rules.
- The server never accepts a price, payout, balance, rank or health value from the client. The client sends intent ("buy item 12"), the server looks up everything else.
- Secrets (the bridge API key) are read on the server through Roblox's secrets store, never placed in scripts, attributes or ReplicatedStorage. *Verify the current Secrets API in Milestone 13.*
- Owner identity: Roblox user ID `2595858454` (the Owner's account, also used for the statue), stored server-side in config.

## 6. Sources of truth

| Data | Owner system | Notes |
|---|---|---|
| Kagundi Dinar balances (bank, cash), transactions | Economy bot ledger | Double-entry, idempotency keys, daily tick at 00:00 Europe/Berlin. Already built in `discord/bot`. |
| Businesses, jobs, wages, loans, credit scores, credit cards, AVK policies and claims, real-estate property, fines, invoices, treasury | Economy bot | Same database |
| Faction membership and ranks | Discord roles assigned through `/roster` | The game reads them through the bridge and caches them per session |
| Discord ↔ Roblox account link | Economy bot (new table) | One-time code shown in game, confirmed with a Discord command (*proposal*) |
| Character identity (RP name, appearance choices), inventory, owned vehicles, licences, spawn preferences | Roblox DataStore (player profile) | Session-locked, versioned |
| Criminal records, case files, court cases, judgments, appeals | Roblox DataStore (world records) | Fines themselves are issued through the bot |
| Map and buildings | Place file | Generated by builders, saved in Studio |

**Decided by Justin (D1, 2026-10-26):** the Roblox game does **not** keep its own money. Every financial action in game (paying, buying, wages for in-game shifts) is sent to the economy bot through an authenticated HTTPS Economy Bridge with a transaction ID. This prevents two economies with conflicting balances. Consequence: a minimal bridge (account link, balance read, idempotent transfer) is built in Milestones 6/7, before the in-game banking front-ends, instead of only in Milestone 13. Until the bridge is online, a `SandboxAdapter` gives test money in Studio only. It is in-memory, clearly labelled as test money, never saved, and refuses to run on live servers.

## 7. Persistence design (detail in Milestone 6)

- DataStoreService with **session locking** so two servers can never write the same profile. Proposal: vendor ProfileStore (open source, by loleris) as one file after checking its license; otherwise a small own implementation on `UpdateAsync`.
- Every profile carries `schemaVersion`; migrations run in order on load and are covered by tests.
- Saves: on change (debounced), every few minutes, on leave and on server shutdown (`BindToClose`), with retries and backoff. A failed load kicks the player with a clear message instead of handing out an empty profile that could overwrite real data.
- World records (cases, incidents) use their own DataStores keyed by record ID, written with `UpdateAsync`.

## 8. World, streaming and performance

- `Workspace.StreamingEnabled = true`. Starting values: target radius about 1,024 studs, minimum radius about 256, integrity mode *pause outside loaded area*. Tuned with measurements in Milestones 2 and 14.
- Buildings are Models with `ModelStreamingMode = Atomic` so they load whole. Only a few critical models (spawn areas) are `Persistent`.
- Client code never assumes a map part exists; it reacts to CollectionService tags appearing and disappearing.
- Starting budgets to measure against (*proposal*): server heartbeat ≥ 55 Hz with 25 players; client memory under about 1.5 GB on desktop and under about 800 MB on mobile; decorative parts non-colliding with simple collision fidelity.
- Server size: 25 players per server. The design must still be correct if Roblox starts a second server (no money or records kept only in server memory).
